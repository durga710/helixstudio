# Helix Studio — System Diagnostic Audit (2026-06)

A read-only review of the deployed codebase after the v3 release, covering mock/demo
data, security, reliability/operations, performance, and UI/accessibility. Findings
are prioritized; each cites a real file. **No code was changed for this report** —
remediation is to be scheduled after review.

Severity scale: **Critical** (fix before real users at scale) · **High** (fix soon) ·
**Medium** (plan it) · **Low** (cleanup / nice-to-have).

---

## 1. Executive summary

The application is architecturally sound. Authorization is consistently enforced
(every sampled API route uses `guard`/`guardWorkspace` with an ownership or
membership check), Prisma parameterizes all queries, passwords use salted scrypt with
constant-time comparison, webhook signatures (git + Stripe) are verified over the raw
body, and file paths are validated against traversal. The new v3 surfaces (plan mode,
activity feed, gradebook, task board) are correctly access-gated.

The issues worth acting on cluster in three areas: (a) a few **security hardening
gaps** — an unsanitized outbound URL, secrets stored in plaintext, and no abuse
controls on signup; (b) **serverless-correctness** of in-memory state (rate limiting
and progress) plus the absence of error monitoring; and (c) a **two-mode design** in
which several non-core screens (`/team`, `/deployments`, `/agents`, `/analysis`) still
serve seeded demo data rather than real persistence. None are exploited today at the
current scale, but they are what stands between this and an "industry-standard" bar.

## 2. Security

### S1 — Outbound SSRF via unsanitized AI base URL · **High**
`src/app/api/preferences/route.ts:97` saves `aiBaseUrl` with only trim/length checks,
while the self-hosted git base URLs right below it (lines 108-114) go through
`sanitizeBaseUrl()` (https-only, no creds). That URL is later passed straight to the
OpenAI client as `baseURL` (`src/lib/ai-agent.ts`, `src/lib/agent-turn.ts:107`). A
signed-in user can point it at `http://169.254.169.254/...` (cloud metadata) or
internal hosts, turning a server-side agent turn into an internal request.
**Fix:** run `aiBaseUrl` through `sanitizeBaseUrl()` too (allow `localhost` for the
local-provider case). ~15 minutes.

### S2 — BYOK API keys & git tokens stored in plaintext · **High**
`UserPreferences` persists `openaiKey`, `anthropicKey`, `localKey`, `githubToken`,
`gitlabToken`, `bitbucketToken`, `azureToken`, `giteaToken` as plaintext columns
(`prisma/schema.prisma`). They are never returned to the client (the GET route returns
only booleans — verified), so this is purely an at-rest concern: a DB compromise leaks
every user's third-party credentials. The cookie-based Anthropic BYOK path
(`src/app/api/keys/route.ts`) is the better model — httpOnly cookie, never persisted.
**Fix:** field-level encryption (a `WORKSPACE_ENC_KEY` + libsodium/`node:crypto`
AES-GCM wrapper at the read/write boundary) or a secrets manager. Rotate after.
Medium effort.

### S3 — No abuse controls on account signup · **High**
`src/app/api/auth/signup/route.ts` has no `guard()`/rate-limit and the Auth.js
credentials sign-in path isn't rate-limited either. Combined with S5 this allows
account-enumeration and signup spam / password brute-force.
**Fix:** add a `guard("auth.signup", { limit: 5, windowMs: 3600_000 })`-style check
keyed by IP, and a backoff on repeated failed credential logins. Small, but depends on
S5 for real teeth.

### S4 — `/space/join/[code]` is a state-changing GET · **Medium**
`src/app/space/join/[code]/route.ts` adds membership on GET. It must be a route
handler (it sets cookies and runs outside the auth-gated layout), but a GET that
mutates is CSRF-shaped: a crafted link makes a signed-in user silently join a space.
Impact is low (needs a valid leaked code, idempotent, only adds membership, never
destroys data), but it's a real deviation from "GET is safe."
**Fix:** keep the GET landing page but perform the actual join via a POST the landing
page issues (or a one-time token in the URL). Small.

### S5 — In-memory rate limiter is per-instance on serverless · **Medium**
*(also a reliability finding — see R1)* `src/lib/rate-limit.ts` keeps buckets in a
process-local `Map`. On Fluid Compute each instance has its own, so effective limits
are `limit × instances`. The file's own comment notes a Redis swap is "one file."
This is what makes S3 and join-code guessing meaningfully easier. **Fix:** Upstash
Redis (or similar) behind the existing interface. Small-to-medium.

### S6 — `/api/health` exposes configuration booleans · **Low**
`src/app/api/health/route.ts` reports which providers/integrations are configured
(booleans only, no values). Useful for monitoring; minor recon aid. **Fix (optional):**
gate the `configured` block behind auth, or keep it — acceptable for many deployments.

**Verified secure (no action):** the full authorization matrix across spaces /
workspaces / assignments / billing / tasks routes; scrypt password hashing; git +
Stripe webhook signature verification (constant-time, raw body); path-traversal guard
`isSafeRepoPath`; no raw SQL; no secrets in client bundles; guest token metering;
classroom-instructor view gating.

## 3. Reliability & operations

### R1 — Per-instance in-memory state on serverless · **High**
Beyond the rate limiter (S5), `src/lib/progress.ts` holds chat tool-progress in a
process-local `Map`. If the client polls `/api/workspaces/[id]/progress` and hits a
different instance than the one running the turn, it sees no progress — an apparently
stuck spinner. `schemaReady()` in `src/lib/db.ts` caches a global promise (fine
within an instance; first-boot races across instances are already handled).
**Fix:** move rate-limit + progress to a shared store (Redis). Medium.

### R2 — No structured logging or error monitoring · **High**
There is no Sentry/Datadog/structured logging — only `console.error`. Background task
crashes (`src/app/api/workspaces/[id]/tasks/route.ts`), webhook failures, and schema
upgrade errors are effectively invisible to operators. A failed payment sync or a
crashing turn could break silently for hours. **Fix:** add Sentry (serverless-friendly)
and log error paths with `{ userId, workspaceId }` context. Small-to-medium.

### R3 — Stripe webhook missing `invoice.payment_failed` · **Medium**
`src/app/api/billing/webhook/route.ts` handles checkout + subscription
created/updated/deleted, but not payment failure. With the 3-day grace in
`src/lib/billing.ts`, a space whose payment fails on day 1 stays "active" until
`currentPeriodEnd + 3d` (potentially ~27 more days). Idempotency itself is fine (the
handler re-derives state from the subscription object). **Fix:** handle
`invoice.payment_failed` (flag, or downgrade after a defined dunning window) and
document the intended grace behavior. Small.

### R4 — Inconsistent API response envelopes · **Medium**
Most routes use the `ok()`/`apiErrors` envelope, but `/api/health`,
`/api/deployments`, `/api/memory`, `/api/keys`, `/api/repos` return bare
`Response.json(...)`. Clients that assume `{ ok, data|error }` must special-case these.
**Fix:** standardize on the envelope (or document the exceptions). Small.

### R5 — Orphaned sandbox VMs not reclaimed · **Medium**
`src/lib/runner/vercel-sandbox.ts` self-destructs previews after 15 minutes (good) and
stops the VM on a write failure, but a workspace row can keep an `envSandbox` name
pointing at a dead VM after a crash/timeout; the next run silently creates a fresh one.
Leaky rather than broken. **Fix:** null stale `envSandbox` on read-failure, or a
periodic cleanup. Small.

## 4. Performance

Largely healthy. **No action** required on: the gradebook (three batched queries, no
N+1), Monaco (dynamically imported / code-split in `workspace-panel.tsx`), and DB
indexes (the hot paths — workspace list, message history, board, assignments,
submissions, activity — all have matching `@@index`es).

### P1 — `/api/spaces/[id]` shared-workspaces query is unbounded · **Low**
`src/app/api/spaces/[id]/route.ts` loads all shared workspaces with per-row `_count`
of files/messages. Prisma batches it (not an N+1), but there's no `take`, so a space
with hundreds of shared workspaces would return a large, slow payload. **Fix:** add a
`take: 100` (plus paging if needed). Small.

### P2 — File tree refetched every chat turn · **Low**
`runAgentTurn` lists the workspace tree (and for imports, refetches from the git host)
on each turn to build context. Correct, but for large imported repos it adds latency
per message. The request-scoped tool cache already avoids a second fetch within a turn.
**Fix (optional):** short-TTL cache of the tree per workspace. Medium; only if users
report slowness on big repos.

## 5. UI / accessibility

Per `docs/DESIGN_SYSTEM.md` (every component needs loading/error/empty/hover/focus
states; WCAG, keyboard nav, contrast). The new screens generally do this well — the
assignment and gradebook screens have proper loading/error/empty states, icon-only
buttons carry `aria-label`s, the board has keyboard ◀/▶ fallbacks alongside drag, and
Radix dialogs trap/restore focus. Gaps:

### U1 — Gradebook table doesn't adapt to small screens · **High (UX)**
`src/components/screens/gradebook-screen.tsx` renders a students × assignments table in
an `overflow-x-auto` card. With many assignments it becomes a wide horizontal-scroll
maze on tablets/phones; headers are 12.5px and truncated. **Fix:** a stacked/card
layout under `md:`, or a column picker. Medium.

### U2 — Board assignee control is invisible until discovered · **Medium**
`src/components/screens/space-board.tsx` overlays an `opacity-0` `<select>` on the
assignee chip. It's screen-reader labeled and clickable, but sighted users get no
affordance that it's interactive. **Fix:** a visible hover/focus state on the chip, or
an explicit "Assign…" button. Small.

### U3 — Small muted text may fail WCAG AA contrast · **Medium**
`text-txt3` at 11.5px appears in several new spots (billing card usage line, board
counts/labels). Likely under the 4.5:1 small-text ratio. **Fix:** confirm the token's
contrast; use `text-txt2` or bump size for load-bearing labels. Small.

### U4 — Dialog inputs don't always autofocus · **Low**
Radix handles the focus trap; adding `autoFocus` to the first field in the new-task /
new-assignment / upgrade dialogs saves a tab. Trivial.

## 6. Mock / demo data inventory

The app is intentionally two-mode: without `DATABASE_URL` it runs a seeded in-memory
store (`src/lib/store.ts`, `src/lib/demo-seed.ts`) and a deterministic mock AI
provider (`src/lib/ai/mock.ts`); with a database + keys, the same routes use real
persistence and real models. **In production (DB + keys set), the core product — auth,
spaces, classrooms, assignments, billing, editor, workspaces, AI — is fully real.**

What remains demo-backed even with a database, because these features were never
ported to Prisma models, and is therefore **user-visible on those specific screens**:

| Surface | What's served | To make real | Effort |
|---|---|---|---|
| `/team` + `/api/team` | seeded members/invites/audit from `store()` | wire to real membership/Invite tables (or fold into Spaces) | M |
| `/deployments` + `/api/deployments` + `/log` | seeded environments/deployments; fake build-log stream; "deploy" makes a fake SHA | Vercel API integration + real build-log streaming | L |
| `/agents` | seeded agent notes; pipeline (`src/lib/agents/pipeline.ts`) returns scripted output when no API key | run the real `runStepReal` path; remove `STEP_SCRIPTS`/`FINAL_OUTPUT` fallback | S–M |
| `/analysis` | seeded analysis (`activeWorkspace().analysis`) | real repo-scan results | M |
| `/api/memory` | `store().memory` rather than the existing `MemoryEntry` model | swap to Prisma (model already exists) | S |
| `/api/terminal` (`npm test`) | hardcoded `TEST_OUTPUT` | execute in the existing sandbox | M |
| mock AI provider | canned plan-style reply when no key configured | require/insert a key, or keep as graceful trial fallback | — |

Appropriate to keep: the demo account + mock provider as a zero-setup trial path, and
the per-feature `!dbEnabled()` empty-state cards (dashboard, editor, spaces, gradebook,
assignments) — those already show "connect a database" rather than fake data.

## 7. Suggested remediation order

1. **S1** (sanitize `aiBaseUrl`) — 15 min, closes an SSRF. Do first.
2. **S5 / R1** (Redis-backed rate limit + progress) — unblocks S3 and fixes the
   stuck-progress UX; the single highest-leverage infra change.
3. **R2** (Sentry + structured logging) — buys visibility for everything else.
4. **S3** (signup rate limit) — trivial once S5 lands.
5. **S2** (encrypt keys at rest) — before onboarding security-sensitive users.
6. **R3** (`invoice.payment_failed`) — before billing carries real revenue.
7. **U1 / U2 / U3** (gradebook responsive, board affordance, contrast) — UX polish.
8. **R4, S4, R5, P1, U4** — cleanup pass.
9. **Mock surfaces** — decide per screen: port to real data, or hide until built. The
   core product doesn't depend on any of them.

Nothing here blocks current usage; this is the path from "works and is correctly
gated" to "hardened and fully real."
